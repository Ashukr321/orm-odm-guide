Document Databases

Store data the way your app reads it: self-contained JSON-like documents instead of rows joined across tables.

01 — Concept

What Is a Document Database?

Data lives in documents (nested objects and arrays), grouped into collections. The schema is flexible, not absent.

SQL: users + addresses + orders
→
JOIN at read time
Document: one user with everything nested
→
Read once
  • MongoDB is the most widely used, storing BSON (binary JSON with Date, ObjectId, Decimal128).
  • Others: Firestore, Couchbase, CouchDB, DocumentDB and Cosmos DB (MongoDB-compatible APIs).

Example

What a Document Looks Like

{
  _id: ObjectId("66f2a1c4e4b0a1b2c3d4e5f6"),
  name: "Ashutosh",
  email: "ashu@example.com",
  addresses: [
    { type: "home", city: "Patna",     pin: "800001" },
    { type: "work", city: "Bengaluru", pin: "560001" }
  ],
  preferences: { theme: "dark", newsletter: true },
  createdAt: ISODate("2026-09-24T10:00:00Z")
}

One read returns the whole user, no joins. ObjectId's first 4 bytes are a timestamp, so _id values sort roughly by insert time.

03 — The Key Decision

Embed vs Reference

Embed when
  • The child is read together with its parent
  • The list is bounded (1–5 addresses)
  • The child is rarely queried on its own
Reference when
  • The data is shared (a product in many orders)
  • The list grows without bound (comments, logs)
  • It changes often and would need many updates
Hard limit — a document can't exceed 16 MB. Unbounded arrays will hit it, and get slow long before they do.
Node.js

CRUD With the mongodb Driver

const users = client.db('app_db').collection('users');

const { insertedId } = await users.insertOne({
  name: 'Ashutosh', addresses: [{ type: 'home', city: 'Patna' }],
});

// dot notation reaches into nested fields
const inPatna = await users.find({ 'addresses.city': 'Patna' }).toArray();

// operators change only the named fields
await users.updateOne({ _id: insertedId }, {
  $set:  { 'preferences.theme': 'dark' },
  $push: { addresses: { type: 'work', city: 'Bengaluru' } },
});

await users.deleteOne({ _id: insertedId });

Use $set, $inc, $push, $pull. Replacing the whole document can overwrite changes made by other requests at the same time.

Node.js

Aggregation — MongoDB's GROUP BY / JOIN

orders.aggregate([
  { $match:  { status: 'paid' } },
  { $unwind: '$items' },
  { $group:  { _id: '$userId',
               revenueMinor: { $sum: { $multiply: ['$items.priceMinor', '$items.qty'] } } } },
  { $lookup: { from: 'users', localField: '_id', foreignField: '_id', as: 'user' } },
  { $sort:   { revenueMinor: -1 } },
  { $limit:  10 },
]);

$lookup is a left outer join. If a hot read needs it every time, the data probably should have been embedded.

04 — Performance

Indexes

users.createIndex({ email: 1 }, { unique: true });           // unique
orders.createIndex({ userId: 1, createdAt: -1 });            // compound
users.createIndex({ 'addresses.city': 1 });                  // multikey (arrays)
posts.createIndex({ title: 'text', body: 'text' });          // text search
sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 }); // TTL
orders.createIndex({ userId: 1 },
  { partialFilterExpression: { status: 'pending' } });       // partial
  • Compound index order follows the ESR rule: Equality → Sort → Range.
  • Run .explain('executionStats'). You want IXSCAN, not COLLSCAN.
Trade-off

Flexible Schema: Feature and Risk

  • ✅ Add a field without a migration
  • ✅ Different shapes in one collection
  • ❌ Typos like emial, age: "twenty", and missing required fields all get saved
db.createCollection('users', {
  validator: { $jsonSchema: {
    bsonType: 'object',
    required: ['email', 'createdAt'],
    properties: {
      email:     { bsonType: 'string' },
      createdAt: { bsonType: 'date' },
    },
  } },
});

Add the schema back where it matters: a database-level $jsonSchema validator, or an ODM like Mongoose in app code.

05 — Correctness

Consistency & Transactions

Single-document writes are atomic — good embedding removes the need for most transactions.
Multi-document ACID transactions — available on replica sets (4.0+) and sharded clusters (4.2+). They cost more, so use them for real cross-document rules like moving money.
Write concern — the default w: "majority" (5.0+) waits until most replicas confirm the write.
Read preference — secondaries can be slightly behind. Read from the primary when you need the latest data.

Interview-Ready Summary

What to Say Cold

  • Self-contained JSON-like documents in collections. The schema is flexible, not absent.
  • Embed data that is bounded and read together. Reference data that is shared or unbounded. Remember the 16 MB limit.
  • Single-document writes are atomic. Multi-document transactions exist but cost more.
  • Index hot queries (ESR rule) and check with explain().
  • Add validation back with $jsonSchema or Mongoose.
  • Replica sets give availability. Sharding gives scale, and the shard key is close to permanent.
