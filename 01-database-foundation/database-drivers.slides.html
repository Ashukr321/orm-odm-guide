01 — Concept

What Is a Database Driver?

The low-level library that speaks a database's wire protocol: opens the connection, authenticates, sends query bytes, parses the raw response.

  • No ORM/ODM talks to the database directly — they all delegate to a driver.

02 — Why It Matters

Why Learn the Driver If You Use an ORM?

  • Raw queries when the ORM's generated SQL isn't optimal.
  • Debugging — pooling, timeouts, prepared statements are driver-level behavior the ORM inherits.
  • Features the ORM hides — Postgres LISTEN/NOTIFY, cursors, streaming large result sets, JSONB operators.
  • Interview signal — "I use Prisma" is tooling; "Prisma still relies on connection pooling the same way pg.Pool does" is systems understanding.
Node.js

PostgreSQL — pg

npm install pg
const { Pool } = require('pg');

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
});

async function getUserById(id) {
  const { rows } = await pool.query(
    'SELECT * FROM users WHERE id = $1',
    [id]
  );
  return rows[0];
}

Use Pool, never a lone Client — and always parameterize queries ($1, $2…), never string-concat values.

Node.js

MySQL — mysql2

const mysql = require('mysql2/promise');

const pool = mysql.createPool({
  host: 'localhost',
  user: 'root',
  password: 'secret',
  database: 'app_db',
  waitForConnections: true,
  connectionLimit: 10,
});

async function getUserById(id) {
  const [rows] = await pool.query(
    'SELECT * FROM users WHERE id = ?',
    [id]
  );
  return rows[0];
}

mysql2 is the modern, Promise-native successor to the old mysql package — prefer it in all new code.

Node.js

MongoDB — native mongodb driver

const { MongoClient } = require('mongodb');

const client = new MongoClient(process.env.MONGO_URI);
let db;

async function connectDB() {
  if (db) return db;
  await client.connect();
  db = client.db('app_db');
  return db;
}

async function getUserById(id) {
  const database = await connectDB();
  return database.collection('users').findOne({ _id: id });
}

MongoClient already manages its own connection pool — reuse one instance for the app's lifetime.

03 — The Core Idea

Connection Pooling

Opening a TCP/TLS connection is expensive. A pool keeps connections open and reused instead of reconnecting per query.

  • Too small → requests queue for a free connection.
  • Too large → hits the database's hard connection limit (Postgres default: 100), and can take the server down.
  • Rule of thumb: pool size relates to (DB connection limit ÷ number of app instances), not "as high as possible."

This one idea is why Next.js on serverless needs special handling — next.

Next.js

Problem 1 — Hot Reload Leaks Pools (dev only)

Dev mode clears the module cache on every file save. A pool created at module scope gets recreated — and the old one never closes.

// lib/db.js
import { Pool } from 'pg';

const globalForPg = globalThis;

export const pool =
  globalForPg.pgPool ??
  new Pool({ connectionString: process.env.DATABASE_URL, max: 10 });

if (process.env.NODE_ENV !== 'production') {
  globalForPg.pgPool = pool;
}

Same globalThis caching pattern the Prisma docs use for PrismaClient — not Prisma-specific, it applies to any client instantiated at module scope.

Next.js

Problem 2 — Serverless Scale-Out

Each invocation can be a fresh isolated instance. 10-connection pool × 50 concurrent instances = 500 connections — past most managed Postgres limits.

Fix 1 — put a pooling proxy in front (PgBouncer, or managed: Neon / Supabase / RDS Proxy).
Fix 2 — keep max low per instance (1–5), you're one of many concurrent instances.
Fix 3 — prefer HTTP/WebSocket-based serverless drivers (@neondatabase/serverless, PlanetScale).
Fix 4 — reuse the client across warm invocations via the same globalThis pattern (Node.js runtime only).
Edge Runtime

Problem 3 — Edge Can't Use Most Node.js Drivers

export const runtime = 'edge' runs in a V8 isolate — no raw TCP socket API. pg, mysql2, and the standard mongodb driver simply don't work there.

  • Default to the Node.js runtime for anything using a traditional driver.
  • Need Edge anyway? Use an HTTP-based driver: @neondatabase/serverless, @vercel/postgres, @planetscale/database, or MongoDB's Data API.
// app/api/users/[id]/route.js
import { pool } from '@/lib/db'; // globalThis-cached pool

export async function GET(_req, { params }) {
  const { rows } = await pool.query(
    'SELECT * FROM users WHERE id = $1',
    [params.id]
  );
  if (!rows[0]) return Response.json({ error: 'Not found' }, { status: 404 });
  return Response.json(rows[0]);
}
04 — Where Each Layer Fits

Driver vs ORM vs ODM

LayerExampleTalks To
Driverpg, mysql2, mongodbDatabase wire protocol directly
ORMPrisma, Sequelize, TypeORMDriver (or own engine, same protocol)
ODMMongoosemongodb driver

Most real apps use an ORM/ODM for ~95% of queries and drop to the raw driver — often exposed by the ORM itself (prisma.$queryRaw, sequelize.query()) — for the rest.

Interview-Ready Summary

What to Say Cold

  • A driver implements a database's wire protocol; ORMs/ODMs are built on top of one.
  • Always use a connection pool, sized relative to the DB's connection limit — not per-app intuition.
  • Next.js, two failure modes to know cold:
    • Dev hot reload → cache the pool on globalThis.
    • Serverless scale-out → pooling proxy or HTTP-based serverless driver, not a bigger max.
  • Edge Runtime can't use standard Node.js drivers — needs HTTP/WebSocket drivers, or run on the Node.js runtime instead.
