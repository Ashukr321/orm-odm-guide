01 — Concept

What Is a Relational Database?

Data lives in tables of rows and columns, linked by keys, and you read and write it with SQL.

PostgreSQL

An Example Schema

CREATE TABLE users (
  id     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email  TEXT NOT NULL UNIQUE,
  name   TEXT NOT NULL
);

CREATE TABLE orders (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id  BIGINT NOT NULL REFERENCES users(id),
  status   TEXT NOT NULL DEFAULT 'pending'
           CHECK (status IN ('pending','paid','shipped','cancelled'))
);

CREATE TABLE order_items (          -- join table (many-to-many)
  order_id          BIGINT REFERENCES orders(id) ON DELETE CASCADE,
  product_id        BIGINT REFERENCES products(id),
  qty               INT    NOT NULL CHECK (qty > 0),
  unit_price_minor  BIGINT NOT NULL,   -- price snapshot, never FLOAT
  PRIMARY KEY (order_id, product_id)
);

The database enforces these for every client: your API, scripts, admin tools. App-level validation can be bypassed. Constraints can't.

04 — Design

Normalization: Store Each Fact Once

1NF — one value per cell. No lists like "Keyboard, Mouse", so split them into order_items rows.
2NF — every non-key column depends on the whole key. product_name depends only on product_id, so move it to products.
3NF — non-key columns depend only on the key. customer_city belongs to the customer, not the order, so move it to users.

Aim for 3NF by default. Denormalize on purpose, with a reason, like the price snapshot on order_items.

SQL

Joins & Aggregation

-- LEFT JOIN: every user, even those with zero orders
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;

-- Revenue per product, only products above ₹10,000 (values in paise)
SELECT p.name, SUM(oi.qty * oi.unit_price_minor) AS revenue_minor
FROM order_items oi
JOIN products p ON p.id = oi.product_id
GROUP BY p.id, p.name
HAVING SUM(oi.qty * oi.unit_price_minor) > 1000000
ORDER BY revenue_minor DESC;

INNER = only matches · LEFT = all left rows plus matches or NULL · WHERE filters rows, HAVING filters groups.

06 — Performance

Indexes

CREATE INDEX orders_user_created_idx ON orders(user_id, created_at DESC);

EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC LIMIT 10;
-- want: "Index Scan using orders_user_created_idx", not "Seq Scan"
  • Leftmost-prefix rule: (user_id, created_at) helps queries on user_id, but not on created_at alone.
  • PostgreSQL indexes PK and UNIQUE columns automatically, but not foreign keys.
  • Every index slows down writes. Index real query patterns, not every column.
Node.js

Transactions With pg

const client = await pool.connect();      // ONE client for the whole transaction
try {
  await client.query('BEGIN');
  const { rows: [order] } = await client.query(
    'INSERT INTO orders (user_id) VALUES ($1) RETURNING id', [userId]);
  await client.query(
    `INSERT INTO order_items (order_id, product_id, qty, unit_price_minor)
     SELECT $1::bigint, id, $3::int, price_minor FROM products WHERE id = $2`,
    [order.id, productId, qty]);
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}

Never send BEGIN through pool.query(). Each call can use a different connection. Always parameterize ($1), never concatenate strings.

Interview-Ready Summary

What to Say Cold

  • Tables linked by primary and foreign keys, queried with SQL.
  • Constraints make the database enforce data rules for every client.
  • Normalize to 3NF, and denormalize only on purpose (price snapshots).
  • ACID makes multi-step changes all-or-nothing. Defaults: PostgreSQL Read Committed, MySQL Repeatable Read.
  • B-tree indexes follow the leftmost-prefix rule. PostgreSQL doesn't index FKs automatically.
  • Scale in order: tune → pool → bigger machine → replicas → partition → shard.
