Database Foundation

SQL vs NoSQL

Not "which is better", but which fits the shape of your data and how you read and write it.

PostgreSQL MongoDB · Redis · Cassandra · Neo4j ACID · CAP
01 — Concept

Two Ways to Store Data

SQL
  • Tables with a fixed schema
  • Linked by keys, queried with SQL
  • Built for correctness, relationships, flexible queries
NoSQL
  • "Not only SQL": four families
  • Each optimized for a specific access pattern
  • Built for known queries at large scale

The right question: what shape is the data, and how will it be read and written?

Example

Same Data, Modeled Both Ways

-- SQL: normalized, JOIN on read
SELECT u.name, a.city
FROM users u
JOIN addresses a
  ON a.user_id = u.id
WHERE u.id = 1;
// MongoDB: shaped around the read
{
  _id: ObjectId("..."),
  name: "Ashutosh",
  addresses: [
    { city: "Patna" },
    { city: "Bengaluru" }
  ]
}
db.users.findOne({ _id: userId });

SQL can answer any question later. The document model makes the planned read fast. Redis (GET session:9f2c1a) can only look up by key, but does it very fast.

Trade-off

Schema: On-Write vs On-Read

On-write (SQL)On-read (NoSQL)
Checked whenInsert / updateYour code reads it
New fieldMigrationJust start writing it
Bad dataRejected by the DBSaved, found later as a bug
Old recordsAll the same shapeSeveral shapes to handle

The schema doesn't disappear, it moves into your app. Teams add it back with $jsonSchema or Mongoose.

04 — Consistency

ACID vs BASE, and CAP

ACID — Atomic, Consistent, Isolated, Durable. A committed transaction is correct and permanent.
BASE — Basically Available, Soft state, Eventually consistent. Replicas may disagree briefly, then converge.
CAP — during a network partition, choose Consistency or Availability. It is not "pick any 2 of 3".
PACELC — even with no partition, you trade latency against consistency.
05 — Reality Check

Common Myths

MythReality
"NoSQL is faster"Only for the access pattern it was designed for
"NoSQL has no schema"The schema lives in your code instead
"SQL can't scale"Replicas, partitioning and distributed SQL go very far
"Mongo has no transactions"Multi-document ACID since 4.0
"SQL can't do JSON"PostgreSQL JSONB with GIN indexes
PostgreSQL

JSONB: The Best of Both

CREATE TABLE products (
  id          BIGINT PRIMARY KEY,
  name        TEXT NOT NULL,
  price_minor BIGINT NOT NULL,
  attributes  JSONB NOT NULL DEFAULT '{}'   -- differs per product type
);
CREATE INDEX products_attributes_idx ON products USING GIN (attributes);

SELECT name FROM products
WHERE attributes @> '{"color": "black", "wireless": true}';

Keep strict, relational fields as columns. Put flexible, rarely joined attributes in JSONB.

06 — Decision

How to Decide

  • Relational data with rules across entities (money, inventory)? → SQL
  • Ad-hoc queries or reporting you can't predict? → SQL
  • Self-contained records, read whole, different shapes? → Document
  • Only lookup by key, needs to be very fast? → Key-value
  • Huge writes, known query per partition? → Wide-column
  • The relationships are the question? → Graph
  • Still unsure? → PostgreSQL (+ JSONB)

Interview-Ready Summary

What to Say Cold

  • SQL: tables, fixed schema, joins, ACID, ad-hoc queries. NoSQL: four families, each for one access pattern.
  • Schema-on-read moves the schema into your code. It doesn't disappear.
  • CAP: during a partition, choose C or A. Not "2 of 3". PACELC adds latency vs consistency.
  • SQL scales further than the myths say. NoSQL scales out by giving up joins.
  • Choose by data shape and access pattern. Default to PostgreSQL when unsure.
  • Real systems are polyglot: SQL core, Redis cache, document or search where it fits.
